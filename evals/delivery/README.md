# Сравнение доставки снимка и shared

Это явный диагностический запуск трёх пар задач для одного Codex CLI. Он не входит в `tests/run.ps1`, не запускается структурной проверкой и не является автоматическим судом качества.

Результат Phase 1: [наблюдения и ограничения](RESULTS.md), [измеренные данные](results.json).

`scenarios.json` хранит одинаковые задачи и синтетические материалы для обеих сторон. `reviewCriteria` остаются у проверяющего: runner не помещает их в проект и не передаёт модели. Первая задача не просит вручную прочитать CORE. В каждом проекте есть заранее изменённый `OWNER_NOTES.md`, который нельзя менять.

Пары проверяют постоянное правило и локальный контекст; выбор QUALITY/RESEARCH для flaky/CI; явный project-audit на небольшой границе с потерянным подтверждением. Они не измеряют визуальное качество или поведение других агентов.

## Подготовка и явный запуск

Сначала проверка формата без записи и обращения к агенту:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/eval-shared-delivery.ps1 -ValidateOnly
```

Затем подготовка одноразовых проектов и локальной установки:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/eval-shared-delivery.ps1
```

Без `-Execute` агент не запускается. После проверки runner и подготовки можно явно собрать поведение:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/eval-shared-delivery.ps1 -Execute
```

`SourceRevision` по умолчанию — текущий HEAD. Runner создаёт чистый локальный clone этой ревизии без сети через `--local --no-hardlinks --no-checkout` и detached checkout. Исходные Git metadata не меняются; незакоммиченные изменения источника не становятся каноническими правилами эксперимента. Снимок подключается существующим `ai-rules.ps1`, shared — проверенным прототипом `scripts/shared-kit.ps1`. Новые шаблоны инструментов и adapter принадлежат прототипу; нормализованные хеши выбранных общих правил, локальные файлы и закреплённая ревизия проверяются до каждой попытки. Коммиты создаются только для синтетической базы одноразовых fixtures; исходный репозиторий не коммитится. Если shell или Git ограничены sandbox среды, сначала восстанови штатное разрешённое выполнение; не меняй security flags одной стороны ради зелёного результата.

Все fixtures, installation и stdout/stderr/последний ответ остаются под `.local-docs/delivery-eval/`. Runner не удаляет их и не переносит результаты в tracked-каталоги. Сводку также нужно проверить перед публикацией. Произвольные команды, stderr и текст ответа находятся только в приватных файлах; сводка сохраняет безопасные идентификаторы, хеши и наблюдённые числовые данные.

## Сопоставимость и ограничения

Обе стороны используют один native executable, `--ignore-user-config --ephemeral --json --sandbox read-only`, `approval_policy=never` и одинаковые безопасно извлечённые top-level scalar `model`/`model_reasoning_effort`, если они доступны. Настроенная модель сохраняется через одинаковый `-c`. Если её отвергает native CLI, отдельный `-Model` позволяет явно выбрать одну поддержанную модель для всех пар повторного эксперимента; предыдущие ошибки и основание замены сохраняются. Если scalar не удалось разрешить, runner фиксирует CLI по умолчанию и неизвестную фактическую модель. Он не читает и не копирует authentication; CLI использует существующий CODEX_HOME. Другие пользовательские config-настройки намеренно не переносятся. Документированные механизмы: [Codex CLI reference](https://developers.openai.com/codex/cli/reference) и [non-interactive mode](https://developers.openai.com/codex/noninteractive).

Global `AGENTS.md`/override учитываются наличием и хешем без публикации текста. Глобальные skills, системная политика и sandbox среды могут остаться одинаковыми внешними факторами. Проверяющий должен сопоставить фактические отказы и доступные инструменты; одинаковые CLI flags не доказывают одинаковых runtime-разрешений. Порядок сторон чередуется между сценариями; одним запуском нельзя устранить случайность модели, warm cache или дрейф сервиса.

При блокировках конкретного способа чтения `-UseRipgrepForReads` добавляет одинаковое ограничение одиночных команд `rg -n` во все задачи повторного запуска. Оно не указывает прочитать CORE или конкретную тему и не меняет права sandbox. Фактический `taskSha256` включает этот префикс; `readingConstraint` отмечает изменение условий. Такой повтор оценивается отдельно от исходного запуска, который сохраняется со всеми отказами.

`-ScenarioId explicit-project-audit` ограничивает отдельный повтор одной парой. Используйте его после исправления конкретного маршрута, сохраняя старые наблюдения и явно отмечая новый digest генератора.

`summary.json` оставляет `taskSuccess=null` и `humanReview=pending`. Exit code 0 означает лишь завершение CLI. Командное упоминание имени правила не доказывает чтение: проверяющий смотрит команду, output и порядок. Tokens сохраняются только при наблюдаемом `turn.completed.usage`; отсутствие данных не становится нулём. Фактическая модель остаётся неизвестной, если события её не раскрывают.

Проверь каждую пару по отдельности: совпадение норм/ревизии, задач и локального контекста; route loading; соблюдение полномочий; качество вывода; сохранность dirty sentinel; фактические проверки и оставшиеся unknowns; стоимость. Отдельно отрази ошибки транспорта/доступа и таймауты. Повтор допустим после исправления инфраструктурного дефекта, но исходное неудачное наблюдение сохраняется. Не своди всё к общему числовому баллу и не объявляй преимущество shared по структурным assertions.
