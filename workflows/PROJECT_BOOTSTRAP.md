# Работающая основа проекта

## Когда применять

Используй при старте нового программного проекта или согласованной крупной подсистемы без установленной основы. Обычная feature-задача использует локальный контракт и не запускает процесс повторно. Подход подходит приложениям, сервисам, играм, мобильным продуктам, CLI, библиотекам, автоматизации и обработке данных; готовый пример для стека не обязателен.

`prompt bootstrap -ProjectRoot <путь>` только печатает запрос для существующего каталога. Он не создаёт проект, не устанавливает зависимости и не запускает генератор. Процесс выполняет агент после чтения запроса. `project-bootstrap` можно явно выбрать через `-Topics`, но профиль не устанавливает его автоматически. Читать процесс прямо из хаба достаточно.

## 1. Понять первый результат

Прочитай локальные инструкции, проверь Git, существующий код, настройки и доступные проверки. Уточни только недостающие сведения, влияющие на решение: идею, первый полноценный сценарий, пользователя или оператора, платформу, данные, внешние эффекты и ограничения. Не заставляй владельца повторять известное или отвечать на анкету обо всех будущих функциях.

Отдели новый проект от существующего. Подключение Kit само по себе не разрешает рефакторинг, создание guard, CI или переработку дизайна. В существующей области используй действующие решения; разрывы вне задачи назови отдельно.

## 2. Выбрать подходящую основу

Масштаб и границы определяет [архитектурное правило](../rules/ARCHITECTURE_AND_DATA.md#первоначальная-архитектура). Начни с соглашений платформы и официальных инструментов выбранной технологии. Учитывай ближайшие подтверждённые изменения, а не гипотетический рост.

- Связная утилита может остаться тремя файлами даже при длительном использовании.
- Несколько самостоятельных возможностей приложения получают владельцев; локальное состояние остаётся рядом с интерфейсом, независимые вычисления отделяются по контракту.
- Интеграционный сервис с повторами и сохраняемыми данными требует явных границ сценария, внешнего эффекта и хранения.
- Для игры или мобильной платформы используй её модель выполнения, ресурсов и развёртывания. Структура веб-приложения не является универсальной.

Это примеры рассуждения, а не список архитектур. Сравни альтернативы только при существенном или дорогом в изменении выборе: например, облачное хранение против локального, платформа выпуска или публичный контракт. Рекомендуй подходящий вариант первым; не строй несколько проектов ради сравнения.

Для графического интерфейса выбери направление по [PRODUCT](../rules/PRODUCT.md#визуальное-направление-до-реализации). Без графического интерфейса этот шаг не применяется.

## 3. Показать план и получить решение

Объясни простыми словами, что будет работать после первого шага, почему выбранные средства подходят, какие данные сохраняются и как проверить результат. Назови существенные ограничения, необходимую ручную работу и важный компромисс. Нескольким файлам не нужен отдельный архитектурный отчёт.

До зависимой реализации получи одобрение этой основы. Если конкретная основа и план уже одобрены в текущей задаче, продолжай без повторного разрешения. Установка зависимостей и подключение Kit могут войти в этот план; внешние действия, commit, push и публикация сохраняют собственные границы полномочий.

## 4. Применить только полезные материалы

Проверь, есть ли подходящий материал в [templates/README.md](../templates/README.md#технические-материалы). Прочитай условия применения и совместимые версии только выбранного материала. Используй отдельную настройку, фрагмент или команду, когда это экономит повторную работу. При несовместимости предложи более подходящее решение и кратко объясни причину; отсутствие примера нормально.

Не перезаписывай существующую конфигурацию. Применённый материал принадлежит проекту и не обновляется синхронизацией правил. Не копируй демонстрационные сценарии, все файлы примера или слои выпущенного продукта автоматически. Официальный scaffolder допустим, если это лучший способ получить нужную основу; собственный универсальный генератор не требуется.

Если одобренный план включает Kit, выбери минимальные профили и темы и выполни штатное подключение из указанного хаба. Проверь план перед разрешённым Apply, затем `doctor` и `status`. Не запускай отдельное интервью через `prompt connect` и не запрашивай повторное одобрение того же состава. Обычное подключение меняет только файлы правил; техническая настройка здесь разрешается именно планом bootstrap. Для публичного проекта сохрани local-only и восстановление уникального контекста по профилю.

## 5. Реализовать первый полноценный сценарий

Создавай каталоги вместе с реальной ответственностью. Добавь необходимые команды запуска и прямые проверки поведения. Тесты, проверка типов, линтер, CI и подготовка к развёртыванию выбираются по стеку, риску и задаче; наличие материала в Kit не делает их обязательными.

Если нужна механическая защита устойчивой границы, используй существующий инструмент и проверь разрешённый и запрещённый импорт на изолированной фикстуре. Проверка пустого дерева не доказывает защиту. Учитывай реальные способы импортов проекта; ограниченный пример не гарантирует все связи.

Проверь первый сценарий, значимый отказ по риску и пригодность основы для следующего изменения. Для интерфейса проверь реальные состояния и композицию. Назови точные команды и результаты; тесты, локальный запуск и реальное развёртывание — разные подтверждения. Если важная проверка недоступна, явно оставь её незавершённой.

## 6. Оставить короткий контекст для продолжения

Достаточно существующего README с запуском и проверками и локальных правил с особенностями проекта. Значимый выбор и его причину сохрани один раз в подходящем разделе; отдельные карта, ADR, runbook и handoff появляются только при самостоятельной пользе по [DOCUMENTATION](../rules/DOCUMENTATION.md). Не веди журнал каждой команды.

После выбора читай локальный контракт и решения затронутой области. Пересматривай основу при новой самостоятельной ответственности, внешней границе или подтверждённом неудобстве изменений. Обычная задача не начинает bootstrap заново.

## Готовый запрос

```text
Создай работающую основу проекта в "{{PROJECT_ROOT}}" и реализуй первый полноценный сценарий из моей задачи.

Прочитай локальные инструкции и процесс "{{BOOTSTRAP_WORKFLOW_PATH}}". Хаб доступен рядом с "{{HUB_CLI_PATH}}". Проверь Git и сохрани несвязанные изменения. Используй уже известную идею, первый сценарий и ограничения; уточни только сведения, без которых нельзя выбрать основу.

Определи подходящий масштаб и технологию. Следуй соглашениям выбранной платформы, сохраняя свободу архитектуры. Сравни варианты только для существенных решений. Готовые материалы Kit применяй избирательно; если они не подходят, объясни почему и выбери иной путь. Для продукта без графического интерфейса не запускай дизайн-процесс.

Покажи понятный план с первым работающим результатом и проверками. Получи одобрение до зависимой реализации; уже согласованный конкретный план не требует повторного разрешения. Подключение Kit при необходимости включи в этот план, без отдельного интервью. Затем создай только необходимые части, проверь первый сценарий и оставь минимальный контекст для продолжения.

В существующем проекте используй принятую архитектуру; подключение не разрешает рефакторинг. Не выполняй неразрешённый -Apply, commit, push или публикацию. В конце сообщи результат, команды проверок, непроверенное и существенные ограничения.
```
