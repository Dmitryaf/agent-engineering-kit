# Первоначальная архитектура проекта

## Когда применять

Применяй при создании развиваемого проекта, крупного package/application или подсистемы без установленных границ. Обычная feature-задача использует локальный контракт и не запускает процесс повторно. Для одноразового кода действуют исключения раздела «Первоначальная архитектура» темы `architecture-and-data`.

Обязанность раннего выбора задана архитектурным правилом. Этот процесс помогает выполнить её; архетипы ниже — стартовые модели, а не дополнительный нормативный слой или обязательные имена каталогов.

## Запуск и контекст

В хабе выполни `prompt bootstrap -ProjectRoot <путь>` и передай запрос агенту вместе с целью и первым сценарием. Команда только печатает запрос. Можно также явно выбрать `project-bootstrap` через `-Topics` при подключении нового проекта; ни один профиль не устанавливает процесс автоматически. В подключённом проекте изменение состава проходит обычный план и разрешённый `-Apply`, без ручной правки upstream или lock.

`prompt connect` распознаёт новый проект и предлагает этот следующий шаг, но само подключение меняет только файлы правил. У существующего проекта отсутствующие границы остаются разрывом для отдельной задачи; bootstrap не разрешает перестройку соседних модулей.

Прочитай локальные инструкции и релевантные правила архитектуры, реализации, качества и документации. В неподключённом проекте используй их из указанного хаба; установка правил не является условием чтения. После выбора читай локальный контракт и решения затронутой области, без повторного чтения всех архетипов.

## 1. Определить сценарии и масштаб

Проверь Git, существующий код, настройки и команды проверки. Назови первый сквозной результат, ближайшие реальные сценарии, владельцев состояния и внешние границы. Отдели новый проект от установленной архитектуры и эксперимент с одной обязанностью от запланированного продукта. Не проектируй гипотетические функции.

## 2. Выбрать один архетип

| Тип | Начальная модель | Когда усложнять |
| --- | --- | --- |
| Пользовательский frontend | Композиция → локальные возможности → общий код | Модель, состояние или адаптер имеют независимый контракт либо нужны нескольким областям |
| Сервис / интеграционная система | Сценарии → contracts/model; adapters → contracts | Самостоятельная capability получает модуль; локальные уровни появляются по ответственности |
| Библиотека / CLI | Связное ядро; координация и adapters при реальных внешних границах | Второй сценарий, иной adapter или самостоятельный публичный контракт |

### A. Пользовательский frontend

Пример областей: `app/` для композиции, `features/` для сценариев, `shared/` для подтверждённо общего кода. Импорты: `app → features → shared`, также `app → shared`; запрещены `shared → features/app` и `features → app`. Переходы между возможностями получают явные точки входа по локальному контракту; универсальный запрет не требуется.

Одной возможности достаточно `features/comparison/Comparison.vue`. При самостоятельных расчётах подходит `features/comparison/ui/Comparison.vue` и `features/comparison/model/comparison.ts` с локальным тестом. Не создавай заранее `api/model/ui/hooks/types/utils` в каждой возможности.

Общий API-клиент может находиться в `shared/api/`, клиент одной возможности — рядом с ней. Общая модель, `services`, `stores` и route adapters появляются только с реальным владельцем; модель не зависит от UI и хранилища. Не выноси каждый локальный `computed` или обработчик из компонента. Корневые entrypoints делегируют самостоятельные сценарии их владельцам.

### B. Сервис / backend

Пример областей: `core/model`, `core/application`, `core/contracts`, `infrastructure/` и `modules/<capability>/`. Core содержит общие предметные правила и сценарии, contracts/ports — внешние зависимости; infrastructure реализует конкретные HTTP, messaging и persistence adapters. Точка композиции создаёт adapters и передаёт их application через contracts.

Импорты: `application → contracts/model`, `infrastructure → contracts/model`; core не импортирует infrastructure и presentation. Поток выполнения «сценарий вызывает adapter» не означает импорт конкретного adapter в core. Предметная модель не определяется Telegram, HTTP или БД.

Самостоятельный модуль может иметь локальные `application/model/infrastructure/presentation`, только когда каждый нужен. Общий core не становится складом capabilities. Один обработчик без независимой модели не требует всех слоёв.

### C. Библиотека / CLI

Связная библиотека может остаться несколькими файлами рядом с публичной точкой входа. Для инструмента с независимыми вычислениями и вводом/выводом подходит `core/`, `application/`, `adapters/`: application использует core и необходимые контракты, adapters реализуют внешний доступ, entrypoint собирает зависимости. Core не знает CLI parsing и конкретную файловую/сетевую реализацию. Не вводи ports и пустые уровни в CLI с одной обязанностью.

## 3. Записать локальный контракт

До существенной реализации кратко запиши тип, первые сценарии, один архетип, области и владельцев, разрешённые зависимости и точки входа, запрещённые связи, точку композиции и отсутствующие слои. Укажи причину выбора и условие пересмотра по действующему правилу документации.

Контракт позволяет найти место для UI и логики одной возможности, внешнего доступа, общего кода, новой возможности и композиции. Достаточно нескольких абзацев в `PROJECT_RULES` или существующей карте; отдельный документ по шаблону нужен только при самостоятельной роли. Не дублируй контракт в двух документах. Значимый выбор добавь коротким разделом в существующую карту решений; bootstrap не требует отдельного ADR, таблицы статусов или рабочих отчётов в корне.

## 4. Создать минимальный skeleton и guard

Создавай каталоги вместе с кодом ответственности первого сценария. Будущие области пока могут оставаться записью в контракте. Не добавляй пустые папки, framework scaffolder или собственный движок анализа зависимостей.

Выбери важнейшие устойчивые ограничения: например, запрет `shared → features/app`, `core → infrastructure/presentation` или allowlist корневых entrypoints. Используй существующий линтер либо небольшой script/structural test. Проверь разрешённый импорт и представительное нарушение на изолированной фикстуре; учитывай реальные способы импортов и возвращай ненулевой exit code с понятным сообщением при нарушении. Субъективную связность файла не заменяй числовым лимитом.

Добавь команду в обычные проверки, CI — если это входит в задачу. Успешная проверка пустого дерева не доказывает защиту. При недоступном механизме назови ограничение и незавершённую часть bootstrap.

## 5. Реализовать и проверить первый сквозной сценарий

Проведи результат через выбранных владельцев, проверь основной путь и значимый отказ по риску. Запусти guard на реальном skeleton. Убедись, что у нового кода есть понятное место, композиция делегирует независимое поведение, нет пустых слоёв, разрешённый и запрещённый случаи проверены. Отделяй результат от commit, push и публикации.

## 6. Пересматривать по причинам изменения

Пересмотри стартовую гипотезу при новой capability, реальном повторном использовании, новом adapter, усложнении жизненного цикла состояния или повторяющемся дрейфе. Выделяй одну границу за раз с сохранением поведения, переносом потребителей и обновлением guard и контракта. Удаляй ненужный слой с проверкой импортов и публичных потребителей; шаблон не оправдывает его сохранение. Основания пересмотра и удаления средств организации ведутся по действующему правилу документации.

## Готовый запрос

```text
Подготовь первоначальную архитектуру проекта в "{{PROJECT_ROOT}}" и реализуй первый сквозной сценарий из моей задачи.

Прочитай процесс "{{BOOTSTRAP_WORKFLOW_PATH}}" и релевантные правила из хаба рядом с "{{HUB_CLI_PATH}}", затем локальные инструкции проекта. Проверь Git и сохрани несвязанные изменения. Если цель или первый сценарий не указаны, собери доступный контекст и уточни недостающее до зависимой реализации.

Выбери один минимальный архетип, запиши локальный контракт размещения кода и зависимостей, создай только необходимые части, добавь и проверь архитектурный guard, затем проверь первый сквозной результат. Для существующей области используй установленную архитектуру; не выполняй автоматический рефакторинг. Обычное подключение Kit не входит в реализацию и не расширяет её границы. Не выполняй неразрешённый -Apply, commit, push или публикацию.

Покажи выбранные границы, отсутствующие слои, точные команды и результаты проверок, непроверенное и условия пересмотра. Не объявляй механическую защиту подтверждённой без разрешённого и запрещённого примеров.
```
