# Завершение подключения и первичная проверка

Используйте этот запрос после `init` и первого `update -Apply`. Откройте ИИ-агента в корне проекта. Общие правила уже находятся в `.ai-rules/upstream/`; копировать их в локальные файлы не нужно.

## Готовый запрос

```text
Заверши подключение AI Rules Hub, зафиксируй границу изменений и проверь проект по подключённым правилам.

Границы задачи:
- можно менять только `AGENTS.md`, `.ai-rules/RULESET.md` и `.ai-rules/PROJECT_RULES.md`;
- остальные файлы используй только для чтения;
- не выполняй `commit`, `push`, публикацию, удаление и исправление найденных разрывов;
- сохрани несвязанные изменения владельца.

Этап 1 — завершение подключения:
1. Проверь `git status` и локальные инструкции.
2. Прочитай `.ai-rules/manifest.json`, `.ai-rules/lock.json`, `RULESET.md`, `PROJECT_RULES.md`, `CORE.md`, выбранные профили и все темы подключённого набора.
3. Изучай проект постепенно. Начни с точек входа и карт документации, затем читай только связанные настройки, документы, код и тесты.
4. Не копируй общие правила из `.ai-rules/upstream/`. В `AGENTS.md` оставь короткий маршрут. В `PROJECT_RULES.md` запиши только особенности проекта. В `RULESET.md` запиши причины выбора, исключения и известные разрывы.
5. Заполняй незаполненные места только подтверждёнными данными. Если источник или проверка отсутствует, укажи `не установлен` или `не установлена`. Не создавай для этого новые документы, инструменты или автоматические проверки.
6. Покажи изменения трёх разрешённых файлов и явно сообщи, что подключение завершено. После этого не меняй файлы проекта.

Этап 2 — проверка только для чтения:
7. Для каждого значимого пункта используй один точный статус: `satisfied`, `gap`, `not applicable` или `unknown`. Подтверди вывод файлом, настройкой, командой или наблюдаемым поведением.
8. Проверь архитектурные границы, источники истины, безопасность данных и ИИ-инструментов, публичность документов, проверки проекта, правила сообщений коммитов и основной язык текста.
9. Сравни похожие сценарии, экраны и операции. Проверь, не исправлен ли только один вариант и не нужен ли общий механизм или парная проверка.
10. Оцени путь нового разработчика: точку входа, запуск, карту архитектуры, источники истины, поиск места изменения и команды проверки. Большой файл считай только сигналом. Разрыв есть, если файл смешивает несвязанные задачи или требует читать лишний контекст.
11. Если команда хаба доступна, выполни `doctor` и `status`. Остальные проверки запускай только тогда, когда они не меняют исходные файлы и не оставляют временные данные.

В результате покажи:
- какие из трёх разрешённых файлов изменены и зачем;
- краткую таблицу проверки, начиная с рисков безопасности, данных и критического поведения;
- повторяющиеся разрывы по классам и самый узкий слой исправления;
- неизвестное и способ его проверки;
- отдельные задачи на исправление, но не выполняй их.
```

Точные английские статусы нужны для сравнения результатов разных проектов. Остальной отчёт пишется на основном языке проекта.
