# Переносимые правила

## Как читать набор

Сначала определи задачу по запросу владельца и указанному им контексту. До планирования и изменений прочитай локальные ограничения, CORE и выбранные профили, затем по индексу выбери темы для затронутой области. Установленный набор не требует чтения всех тем. Чтение правила не запускает полный рабочий процесс; его условия и обязанности профиля сохраняются.

[`CORE.md`](CORE.md) обязателен для каждого подключённого проекта. Каждый выбранный профиль читается всегда: он содержит уникальные обязанности типа проекта. В тематических правилах читай применимые разделы, даже если тема входит в композицию профиля. Например, запись решения не требует чтения всей процедуры очистки документации; работа с данными требует соответствующих защитных разделов независимо от масштаба проекта.

Канонический состав профилей и порядок тем задаёт [`../sync/catalog.json`](../sync/catalog.json). Manifest выбирает состав проекта, а status показывает точный effective-набор.

| Документ | Когда обязателен |
| --- | --- |
| [`PRODUCT.md`](PRODUCT.md) | продуктовая функция, требования, UI-текст или приоритизация; выбор направления до существенного нового UI или редизайна, с исключениями для малых правок и действующей системы |
| [`ARCHITECTURE_AND_DATA.md`](ARCHITECTURE_AND_DATA.md) | размещение кода, модели, хранение, API, миграции; локальный контракт для существующей области, первоначальный выбор до существенной реализации новой области без границ |
| [`IMPLEMENTATION.md`](IMPLEMENTATION.md) | изменение кода, конфигурации или зависимостей |
| [`QUALITY.md`](QUALITY.md) | до реализации для выбора приёмки; проверка и передача изменения |
| [`RELIABILITY_AND_OPERATIONS.md`](RELIABILITY_AND_OPERATIONS.md) | эксплуатация сервиса, деградация, восстановление либо риск производительности или предельной нагрузки |
| [`SECURITY_AND_PRIVACY.md`](SECURITY_AND_PRIVACY.md) | секреты, доступ, личные данные, AI с инструментами, внешние сервисы, публикация; проверка затронутых границ и зависимостей по риску, без автоматического полного аудита и отмены обязанностей профиля |
| [`DOCUMENTATION.md`](DOCUMENTATION.md) | значимый выбор или пересмотр решения; создание или изменение документации и рабочего контекста |
| [`GIT_AND_DELIVERY.md`](GIT_AND_DELIVERY.md) | до изменения веток, индекса или истории Git; коммиты, CI/CD, релиз или внешняя операция; обычное чтение git status и diff не запускает процесс доставки |
| [`AI_COLLABORATION.md`](AI_COLLABORATION.md) | распределение работы между человеком и AI, менторский режим |
| [`RESEARCH_AND_EVIDENCE.md`](RESEARCH_AND_EVIDENCE.md) | неизвестный API, исследование, эксперимент, аудит или доказательная рекомендация |
Тематическое правило задаёт нормы для класса задач. Рабочие процессы конкретных задач находятся в [`../workflows/`](../workflows/) и не становятся постоянными нормативными правилами. Для совместимости manifest идентификатор `project-study` пока выбирает `workflows/PROJECT_STUDY.md`; `project-audit` выбирает `workflows/PROJECT_DEEP_AUDIT.md`, а `parallel-delivery` — `workflows/PARALLEL_DELIVERY.md`. Профили не подключают эти процессы автоматически.

Для выбора визуального направления есть отдельный `visual-design-discovery` — [`VISUAL_DESIGN_DISCOVERY.md`](../workflows/VISUAL_DESIGN_DISCOVERY.md). Обязанность до реализации и исключения задаёт `PRODUCT.md`; подробный процесс читается по задаче из хаба или явно выбранной копии. Существующие визуальные системы и малые правки не требуют повторного Discovery.

[`PROJECT_BOOTSTRAP`](../workflows/PROJECT_BOOTSTRAP.md) выбирает основу по первому сценарию и ограничениям, без закрытого списка архитектур. [Технические материалы](../templates/README.md#технические-материалы) необязательны и не являются нормами: агент применяет подходящую часть либо выбирает средства другого стека. Код и настройки после применения принадлежат проекту. Графический дизайн, CI, guard и отдельные карты нужны только при своей задаче или риске.

## Приоритет правил

При конфликте применяй следующий порядок:

1. ограничения среды, безопасности и явно заданная задача пользователя;
2. локальные правила целевого проекта;
3. явно выбранный профиль;
4. релевантные текущей задаче тематические правила;
5. `CORE.md`;
6. примеры и внешние подтверждения.

Более частное правило может уточнить процесс, команды и критерии. Ослабление защиты данных, достоверности, обратимости или контроля владельца должно быть явно названо, обосновано и согласовано; молчаливое исключение недействительно.

## Нормативный язык

- `обязан`, `нельзя`, `только` — обязательное ограничение;
- `следует` — правило по умолчанию, от которого допустимо отступить с записанной причиной;
- `можно` — разрешённый вариант, а не требование;
- пример не создаёт правило сам по себе.

Каждое новое правило должно отвечать на четыре вопроса: где действует, какой риск предотвращает, как его проверить и в каком случае допустимо исключение.
