# Архитектура хаба правил

## Целевой результат

Целевой проект должен получить короткую локальную точку входа и читать только тот набор правил, который относится к его типу и текущей задаче.

```text
запрос владельца и указанный контекст задачи
→ AGENTS.md целевого проекта
→ .ai-rules/RULESET.md с выбранными слоями
→ .ai-rules/PROJECT_RULES.md с локальной спецификой
→ .ai-rules/upstream/CORE.md
→ .ai-rules/upstream/INDEX.md с эффективной картой чтения
→ выбранные профили и релевантные текущей задаче темы
→ документы и код затронутого сценария
```

Хаб остаётся источником шаблонов и обновлений. Подключённый проект владеет локальными правилами, а выбранная копия переносимых правил обновляется явной локальной синхронизацией.

Запрос задаёт область чтения; до планирования и изменений действуют обязательные локальные ограничения, CORE и выбранные профили. Условия чтения тем уточняют объём работы, сохраняя нормативные обязанности и гейты действий. Установленный состав не равен контексту задачи: `CORE → выбранный профиль → релевантные темы → нужный рабочий процесс → локальные разделы`. Полная карта проекта служит пониманию системы человеком; агент выбирает разделы по области и зависимостям. Карта решений ведёт к релевантным основаниям по [правилу документации](../rules/DOCUMENTATION.md#карта-значимых-решений).

## Экспериментальный shared-путь

[Phase 1](SHARED_INSTALL.md) добавляет отдельный маршрут: неизменяемый локальный выпуск → Codex adapter → постоянный сгенерированный блок `AGENTS.md` и выбор проекта → локальные правила. Schema `0.1` в `.ai-rules/shared.json` имеет явные `mode: shared` и `policy: pinned`; manifest/lock `0.2` режима снимка сохраняют прежнее значение. Выпуск для новых подключений выбирается через `selected.json`; существующая связь никогда не меняет закреплённую версию автоматически.

`src/SharedInstall.psm1` собирает поставку из канонических источников и хранит хеши происхождения и целостности. `src/CodexAdapter.psm1` отвечает за точку входа проекта, ссылку для нативного обнаружения Skill и диагностику. `adapters/codex/adapter.json` выбирает точные разделы CORE, а `skills/project-audit.json` задаёт metadata генерации единственного Skill из существующего workflow. Сгенерированный фрагмент и ресурсы выпуска не являются независимо редактируемыми нормативными источниками.

Цена эксперимента — зависимость проекта от доступности внешней установки, directory link и инструкций конкретной среды. Выбор pinned вместо автоматического current предотвращает смену правил в выполняющейся задаче; обновление существующей связи отложено. Контракт пересматривается по результатам парных delivery evals и реального пилота: если доставка не уменьшает обслуживание либо теряет доступность, снимок остаётся допустимым выбором. Это не registry и не массовая миграция.

## Канонические слои

### `rules/CORE.md`

Минимальные правила, применимые почти везде: контекст, границы задачи, достоверность, источники истины, проверка, понятный язык, контроль владельца и честная передача результата.

`CORE.md` должен оставаться коротким. Правило исключается из него, если требует конкретного типа продукта, данных, команды, платформы или режима обучения.

### Тематические `rules/*.md`

Подробные нормы для продукта, архитектуры и данных, реализации, качества, эксплуатации, безопасности, документации, Git, совместной работы с AI и исследований. Каталог включает их в итоговый набор, но агент читает только темы текущей задачи.

Рабочие процессы находятся в `workflows/` и выбираются явно; профили не подключают их автоматически. Совместимые идентификаторы и пути задаёт `sync/catalog.json`, маршрут запуска — [README](../README.md). Команда `prompt` только печатает запрос и не меняет проект.

### `profiles/`

Композиции для повторяющихся типов проектов. Профиль:

- ссылается на темы, а не копирует их;
- содержит только дополнительные обязательства;
- может сочетаться с другими профилями;
- не содержит временное состояние конкретного проекта.

Профиль читается всегда, если выбран. Его каноническая композиция хранится только в `sync/catalog.json`; списки тем не дублируются в Markdown профиля.

### `templates/`

Стартовые формы локальных документов. Незаполненное место не является значением по умолчанию, а комментарий шаблона — нормативным правилом.

### `workflows/`

Инструкции для ограниченного процесса: подключения, первичного аудита или учебного изучения проекта. Workflow применяется только по явной команде или выбранному совместимому идентификатору и не становится нормой для всех задач проекта.

Первоначальный выбор обязан состояться по `ARCHITECTURE_AND_DATA.md` до существенной реализации новой развиваемой области. Всегда читаемый `standard-product`, тема реализации и `INDEX` ведут к этому условию; локальный контракт затем определяет место нового кода. [`PROJECT_BOOTSTRAP.md`](../workflows/PROJECT_BOOTSTRAP.md) содержит только стартовый процесс, три архетипа и запрос `prompt bootstrap` в одном файле. `project-bootstrap` выбирается явно и не входит в композицию профилей. Подключение нового проекта предлагает следующий шаг, существующего — фиксирует разрыв без реализации или рефакторинга. Если процесс не установлен, краткий контракт архитектурного правила остаётся достаточным для первоначального выбора.

Визуальный выбор до существенного нового UI или редизайна задаёт [PRODUCT](../rules/PRODUCT.md#визуальное-направление-до-реализации); `standard-product`, `IMPLEMENTATION` и metadata `INDEX` ведут к нему до кода. [VISUAL_DESIGN_DISCOVERY](../workflows/VISUAL_DESIGN_DISCOVERY.md) содержит подробный процесс и читается только по подходящей задаче, из хаба либо явно выбранной копии `visual-design-discovery`. Профили его не устанавливают; без workflow действует компактный минимум продуктового правила. [QUALITY](../rules/QUALITY.md#проверка-интерфейса) владеет приёмкой направления и антишаблонной проверкой. Это предотвращает выбор привычной композиции без основания, сохраняя существующие системы и границы малых задач. Цена — исследование и сравнение до кода; эффект на дизайн остаётся гипотезой до поведенческих evals. Объём процесса пересматривается при задержках без пользы или смене модели; равноценный более простой путь — основание заменить процесс после сравнения.

### `sync/` и управляемая копия

`sync/catalog.json` задаёт разрешённые значения `topics`, `profiles` и их зависимости. Файл `.ai-rules/manifest.json` выбирает состав, а `.ai-rules/lock.json` хранит точную версию и SHA-256.

`src/EffectiveIndex.psm1` строит `.ai-rules/upstream/INDEX.md` из `sync/catalog.json` и `.ai-rules/manifest.json`. Индекс содержит назначение, условие чтения, вид и путь каждого выбранного элемента. Он входит в `lock.json`, проверяется как любой другой управляемый файл и не редактируется вручную.

Корневой `ai-rules.ps1` объединяет подготовку, просмотр и применение правил. Он обрабатывает аргументы и выводит результат для пользователя, но не вычисляет состояние из текста дочерних процессов.

Внутреннее ядро находится в `src/`:

- `Catalog` проверяет каталог, выбранные профили и темы;
- `Contracts` задаёт типизированные `AiRules.SyncPlan`, `AiRules.ProjectState` и `AiRules.Diagnostic`;
- `PathsAndHashing` реализует безопасные пути, проверку reparse points, SHA-256 и стабильный JSON;
- `GitState` вычисляет revision, dirty state и отношение revisions;
- `EffectiveIndex` строит производную карту чтения без записи на диск;
- `SyncPlan` строит план только для чтения как объект без записи и вывода;
- `ProjectState` один раз читает `manifest.json` и `lock.json`, затем формирует общее состояние для `status` и `doctor`;
- `PublicRepository` определяет физическую границу Git, строит план локального exclude, применяет только этот блок и формирует состояние публикации runtime и доступности Private Project Context; не меняет index и не читает приватное содержимое источника;
- `Diagnostics` преобразует снимок и локальные документы в диагностические результаты.

`scripts/sync-rules.ps1` применяет уже рассчитанный `SyncPlan` и сохраняет текстовый вывод для пользователя. Строка `Summary:` не разбирается внутренним кодом как машинный контракт.

Скрипт проверки запускает дочерние тесты той же версией PowerShell, которой был вызван сам. Обязательная проверка Windows PowerShell 5.1 сохраняет минимальный контракт. Отдельные проверки используют `pwsh` на Windows и, в экспериментальном режиме, на Ubuntu.

```text
hub checkout + project manifest
→ plan
→ add / update / unchanged / conflict / orphan
→ explicit apply
→ .ai-rules/upstream/ + .ai-rules/lock.json
```

Синхронизация владеет только `.ai-rules/upstream/` и сгенерированным `.ai-rules/lock.json`. Корневой `AGENTS.md`, `.ai-rules/RULESET.md` и `.ai-rules/PROJECT_RULES.md` принадлежат проекту и после первого создания не перезаписываются. Ручное изменение файла внутри `.ai-rules/upstream/` считается конфликтом.

Для `public-repository` подготовка и Apply также поддерживают помеченный блок локального Git `info/exclude`. Это отдельная граница хранения, без изменения manifest/lock schema `0.2`. Manifest — канонический выбор состава; lock — воспроизводимый снимок; `upstream/` и `INDEX.md` — производная рабочая копия. Все они по умолчанию local-only, а уникальная конфигурация и проектные правила получают путь восстановления из [Private Project Context](../rules/DOCUMENTATION.md#приватный-источник-публичного-проекта). Приватный источник владеет внутренними основаниями, локальный descriptor только связывает его с проектом. Новый clone не обязан содержать инфраструктуру агента. Private-профили сохраняют допустимое tracked-хранение.

Выбор предотвращает случайную публикацию runtime обычным `git add`; его цена — отдельное подключение после clone и ответственность владельца за сохранение уникальных правил. Сценарии проверяются в [`test-public-repository.ps1`](../tests/cli/test-public-repository.ps1); поведение агента задают [eval-кейсы](../evals/README.md), а их структура не доказывает успешный запуск. Модель пересматривается при появлении подтверждённой потребности распространять правила внешним пользователям. Локальный descriptor можно не использовать, если связь и восстановление уже обеспечены приватными локальными правилами; второй сервис хранения не нужен.

### Адаптеры агентов

`AGENTS.md` остаётся канонической точкой входа проекта. В самом хабе проверяется один пилот для Claude Code: корневой `CLAUDE.md` содержит только импорт `@AGENTS.md`. Этот файл не входит в каталог, шаблоны подключения или управляемую копию и не означает массовое добавление таких файлов.

Для параллельной работы Codex первая версия использует ту же точку входа, явно выбранный `parallel-delivery` и сгенерированный `prompt parallel`. Шаблон `templates/TASK_CONTRACT.md` читается из локального хаба по пути в запросе и не копируется синхронизацией; подключённый процесс перечисляет обязательные поля и остаётся понятным без доступного хаба. Отдельный Codex Skill нужен только после наблюдения повторяющейся ручной механики, которую этот маршрут не устраняет. Штатный Agent Command Center координирует агентов, когда доступен; хаб не запускает их процессы и не ведёт собственное состояние задач.

### `hub/`

Продуктовые и архитектурные правила самого Agent Engineering Kit и решения о структуре.

### `evals/`

Ограниченные воспроизводимые сценарии для проверки поведения агента. `Controls` и `cases` не являются новым нормативным слоем, не входят в управляемый снимок и не участвуют в рабочей синхронизации. Результат оценивается отдельно от текста правил и сохраняет фактические наблюдения, нарушения и неизвестное.

## Граница переносимой политики

- Разделение ответственностей сохраняется как инвариант; `Vue SFC` остаётся только примером допустимой локальной связности.
- Направление зависимостей переносимо, а алиасы, допустимая глубина относительных импортов и их lint-проверки задаются проектом.
- Видимый управляющий поток переносим, а точный стиль скобок и переносов принадлежит formatter/linter-конфигурации проекта.
- Проект обязан определить формат и проверку коммитов. `Conventional Commits` является рекомендуемым вариантом при отсутствии решения, но конкретные `type`, `scope`, язык, `Husky`, `commitlint` или другой hook не являются общей обязанностью.
- Иерархия интерфейса, состояния, адаптивность и доступность остаются task-lazy продуктовыми инвариантами: они применяются к затронутому интерфейсу, а не запускают аудит всего проекта.
- `learning-project` сохраняется только для проекта, в котором разработка постоянно связана с обучением владельца. Разовая учебная задача использует отдельный рабочий процесс с проверкой самостоятельности; темп и предметные задания уточняются локально.
- Карта значимых решений — постоянная практика; каноническое хранение и контракт записей определяет [DOCUMENTATION.md](../rules/DOCUMENTATION.md#карта-значимых-решений). Учебный процесс использует её, но не владеет решениями и не создаёт второй источник их оснований.

## Разрешение конфликтов

Локальная специфика должна побеждать общее правило по умолчанию, иначе правила нельзя применять к разным проектам. Но исключение записывается явно:

```md
## Исключение

- Исходное правило: ...
- Причина: ...
- Заменяющее поведение: ...
- Область действия: ...
```

Исключение не может молча отменить системное ограничение, безопасность среды или явно заданное требование владельца.

## Жизненный цикл правила

Наблюдение → проверка переносимости → профиль или тема → при широкой применимости `CORE` → пересмотр, замена или удаление с описанием перехода. Временный аудит не становится правилом: нужны подтверждения во втором контексте либо фундаментальный риск.

Причина, цена и условия пересмотра значимых правил, профилей и процессов кратко описываются в [существующем описании решения](../rules/DOCUMENTATION.md#пересмотр-средств-организации-работы-агента). Подробные доказательства остаются в исследовании. Новая модель может сделать прежнюю меру лишней; подтверждённое упрощение предпочтительнее накопления. Это не вводит автоматическое удаление управляемых файлов.

Асинхронные гарантии уточняются в существующих IMPLEMENTATION и QUALITY: одиночное успешное состояние не показывает поздний ответ или частично выполненную операцию. Цена — выбор значимых переходов и короткое уточнение исходов; область — затронутые операции с риском потери данных, ложного подтверждения или повторного эффекта. Общая очередь, конкретное хранилище и полный набор сценариев не обязательны. Меру сократи или удали, если сравнение не показывает уменьшения целевых дефектов либо существующий инструмент уже гарантирует нужный контракт без этих указаний. Структурные проверки доставки не доказывают влияние на поведение агента.

Журнал существенных проблем включается решением владельца проекта и читается через локальные правила только перед связанной работой. Он сохраняет причины и ограничения проверок для пересмотра мер; цена — краткая запись до передачи, без отчёта о каждой команде. Если записи не помогают предотвращать повторение или выбирать проверку, форму и маршрут следует упростить. Сокращение журнала сохраняет отдельные механизмы и ссылки на первоначальные свидетельства.

## Что пока не строится

- package registry правил;
- универсальная JSON/YAML-схема всех правил;
- сложная система rule IDs и dependency resolution;
- CI matrix для стеков подключённых проектов.
- удалённая загрузка и автоматическое обнаружение проектов;
- массовое внедрение и автоматическое разрешение конфликтов;
- автоматическое удаление orphan-файлов.

Эти возможности допустимы после реальных подключений, когда станут известны требования к внедрению, конфликтам и закреплению версий.
