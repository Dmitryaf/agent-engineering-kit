# Архитектура хаба правил

## Целевой результат

Целевой проект должен получить короткую локальную точку входа и читать только тот набор правил, который относится к его типу и текущей задаче.

```text
AGENTS.md целевого проекта
→ .ai-rules/RULESET.md с выбранными слоями
→ .ai-rules/PROJECT_RULES.md с локальной спецификой
→ .ai-rules/upstream/CORE.md
→ .ai-rules/upstream/INDEX.md с эффективной картой чтения
→ выбранные профили и релевантные текущей задаче темы
→ документы и код затронутого сценария
```

Хаб остаётся источником шаблонов и обновлений. Подключённый проект владеет локальными правилами, а выбранная копия переносимых правил обновляется явной локальной синхронизацией.

## Слои

### `rules/CORE.md`

Минимальные правила, применимые почти везде: контекст, границы задачи, достоверность, источники истины, проверка, понятный язык, контроль владельца и честная передача результата.

`CORE.md` должен оставаться коротким. Правило исключается из него, если требует конкретного типа продукта, данных, команды, платформы или режима обучения.

### Тематические `rules/*.md`

Подробные нормы для продукта, архитектуры и данных, реализации, качества, эксплуатации, безопасности, документации, Git, совместной работы с AI и исследований. Каталог включает их в итоговый набор, но агент читает только темы текущей задачи.

Рабочие процессы конкретных задач находятся в `workflows/` и не считаются постоянными нормативными правилами. Идентификатор `project-study` пока сохраняется для совместимости `.ai-rules/manifest.json`, но создаёт `workflows/PROJECT_STUDY.md` и не входит ни в один профиль.

### `profiles/`

Композиции для повторяющихся типов проектов. Профиль:

- ссылается на темы, а не копирует их;
- содержит только дополнительные обязательства;
- может сочетаться с другими профилями;
- не содержит временное состояние конкретного проекта.

Профиль читается всегда, если выбран. Его каноническая композиция хранится только в `sync/catalog.json`; списки тем не дублируются в Markdown профиля.

### `templates/`

Стартовые формы локальных документов. Незаполненное место не является значением по умолчанию, а комментарий шаблона — нормативным правилом.

### `workflows/`

Инструкции для ограниченного процесса: подключения, первичного аудита или учебного изучения проекта. Workflow применяется только по явной команде или выбранному совместимому идентификатору и не становится нормой для всех задач проекта.

### `sync/` и управляемая копия

`sync/catalog.json` задаёт разрешённые значения `topics`, `profiles` и их зависимости. Файл `.ai-rules/manifest.json` выбирает состав, а `.ai-rules/lock.json` хранит точную версию и SHA-256.

`src/EffectiveIndex.psm1` строит `.ai-rules/upstream/INDEX.md` из `sync/catalog.json` и `.ai-rules/manifest.json`. Индекс содержит назначение, условие чтения, вид и путь каждого выбранного элемента. Он входит в `lock.json`, проверяется как любой другой управляемый файл и не редактируется вручную.

Корневой `ai-rules.ps1` объединяет подготовку, просмотр и применение правил. Он обрабатывает аргументы и выводит результат для пользователя, но не вычисляет состояние из текста дочерних процессов.

Внутреннее ядро находится в `src/`:

- `Catalog` проверяет каталог, выбранные профили и темы;
- `Contracts` задаёт типизированные `AiRules.SyncPlan`, `AiRules.ProjectState` и `AiRules.Diagnostic`;
- `PathsAndHashing` реализует безопасные пути, проверку reparse points, SHA-256 и стабильный JSON;
- `GitState` вычисляет revision, dirty state и отношение revisions;
- `EffectiveIndex` строит производную карту чтения без записи на диск;
- `SyncPlan` строит план только для чтения как объект без записи и вывода;
- `ProjectState` один раз читает `manifest.json` и `lock.json`, затем формирует общее состояние для `status` и `doctor`;
- `Diagnostics` преобразует снимок и локальные документы в диагностические результаты.

`scripts/sync-rules.ps1` применяет уже рассчитанный `SyncPlan` и сохраняет текстовый вывод для пользователя. Строка `Summary:` не разбирается внутренним кодом как машинный контракт.

Скрипт проверки запускает дочерние тесты той же версией PowerShell, которой был вызван сам. Обязательная проверка Windows PowerShell 5.1 сохраняет минимальный контракт. Отдельные проверки используют `pwsh` на Windows и, в экспериментальном режиме, на Ubuntu.

```text
hub checkout + project manifest
→ plan
→ add / update / unchanged / conflict / orphan
→ explicit apply
→ .ai-rules/upstream/ + .ai-rules/lock.json
```

Синхронизация владеет только `.ai-rules/upstream/` и сгенерированным `.ai-rules/lock.json`. Корневой `AGENTS.md`, `.ai-rules/RULESET.md` и `.ai-rules/PROJECT_RULES.md` принадлежат проекту и после первого создания не перезаписываются. Ручное изменение файла внутри `.ai-rules/upstream/` считается конфликтом.

### Адаптеры агентов

`AGENTS.md` остаётся канонической точкой входа проекта. В самом хабе проверяется один пилот для Claude Code: корневой `CLAUDE.md` содержит только импорт `@AGENTS.md`. Этот файл не входит в каталог, шаблоны подключения или управляемую копию и не означает массовое добавление таких файлов.

### `hub/`

Продуктовые и архитектурные правила самого Agent Engineering Kit и решения о структуре.

### `evals/`

Ограниченные воспроизводимые сценарии для проверки поведения агента. `Controls` и `cases` не являются новым нормативным слоем, не входят в управляемый снимок и не участвуют в рабочей синхронизации. Результат оценивается отдельно от текста правил и сохраняет фактические наблюдения, нарушения и неизвестное.

## Граница переносимой политики

- Разделение ответственностей сохраняется как инвариант; `Vue SFC` остаётся только примером допустимой локальной связности.
- Направление зависимостей переносимо, а алиасы, допустимая глубина относительных импортов и их lint-проверки задаются проектом.
- Видимый управляющий поток переносим, а точный стиль скобок и переносов принадлежит formatter/linter-конфигурации проекта.
- Проект обязан определить формат и проверку коммитов. `Conventional Commits` является рекомендуемым вариантом при отсутствии решения, но конкретные `type`, `scope`, язык, `Husky`, `commitlint` или другой hook не являются общей обязанностью.
- Иерархия интерфейса, состояния, адаптивность и доступность остаются task-lazy продуктовыми инвариантами: они применяются к затронутому интерфейсу, а не запускают аудит всего проекта.
- `learning-project` сохраняется только для проекта, в котором разработка постоянно связана с обучением владельца. Разовая учебная задача использует отдельный рабочий процесс, а подробные правила наставничества остаются локальными.

## Разрешение конфликтов

Локальная специфика должна побеждать общее правило по умолчанию, иначе правила нельзя применять к разным проектам. Но исключение записывается явно:

```md
## Исключение

- Исходное правило: ...
- Причина: ...
- Заменяющее поведение: ...
- Область действия: ...
```

Исключение не может молча отменить системное ограничение, безопасность среды или явно заданное требование владельца.

## Жизненный цикл правила

```text
наблюдение или повторяющийся риск
→ проверяемые примеры и подтверждения
→ кандидат и проверка переносимости
→ профиль или тематическое правило
→ при подтверждении широкой применимости — `CORE.md`
→ уточнение, замена или удаление с migration note
```

Временный аудит не переносится напрямую в `CORE.md`. Сначала из него извлекается устойчивое решение, затем оно проверяется минимум на втором контексте или на фундаментальном риске вроде потери данных.

## Что пока не строится

- package registry правил;
- универсальная JSON/YAML-схема всех правил;
- сложная система rule IDs и dependency resolution;
- CI matrix для стеков подключённых проектов.
- удалённая загрузка и автоматическое обнаружение проектов;
- массовое внедрение и автоматическое разрешение конфликтов;
- автоматическое удаление orphan-файлов.

Эти возможности допустимы после реальных подключений, когда станут известны требования к внедрению, конфликтам и закреплению версий.
